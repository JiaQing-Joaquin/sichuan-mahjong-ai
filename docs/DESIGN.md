## 1. 项目定位与目标

### 1.1 定位

| 项 | 内容 |
|---|---|
| 玩法 | 四川麻将·血战到底（108 张，四人） |
| 产品形态 | 商业对战产品中的 AI 对手 / 陪练 / 复盘 |
| 部署 | 服务端无状态推理；离线批量训练与评估 |
| 技术栈 | Python（规则/研究）→ 热点可下沉 Rust/C++；PyTorch 训练 |

### 1.2 分阶段强度目标

1. **阶段 A（已完成）**：规则基线，稳定强于普通玩家与随机策略。
2. **阶段 B**：监督学习（BC），对基线胜率 ≥ 55%。
3. **阶段 C**：自博弈强化学习（RL），对阶段 B 胜率 ≥ 55%，平均得分显著提升。
4. **阶段 D**：接近高水平真人，平均名次 ≤ 2.0。

### 1.3 成功指标

| 维度 | 指标 | 目标 |
|---|---|---|
| 正确性 | 单元/整局测试 | 全绿，随机对局零崩溃 |
| 强度 | 对基线平均得分 | 阶段 B > +0.5/局；阶段 C > +2/局 |
| 强度 | 对真人平均名次 | ≤ 2.0 |
| 延迟 | 单步决策 P99 | < 50 ms（CPU 推理） |
| 稳定性 | 新旧版本胜率 | ≥ 52% 才允许上线 |

### 1.4 非目标

- 不做真实货币/博彩功能（合规红线，见 §13）。
- 不做前端 UI；引擎只暴露状态与动作接口。
- v1 不做换三张与抢杠胡的完整实现（见 §2.7 / §12.2）。

## 2. 规则规格

> 规则正确性是整个项目的地基：规则错一点，训练出来的策略全错。所有规则细节必须可测试、可配置。

### 2.1 牌与流程

- **108 张**：万 / 筒 / 条各 1–9，每种 4 张；**无风牌、字牌、花牌**。
- 四人；庄家 14 张，闲家 13 张；庄家先出牌。
- **不能吃**，只能碰、杠。
- 杠：明杠（碰别人打出的牌）、暗杠（手里 4 张）、补杠（已碰再摸到第 4 张）；杠后补摸一张。

### 2.2 定缺（缺一门）

- 开局每人选定一门作为「缺」，胡牌前必须打光该门。
- 缺门牌不能碰、不能杠；手中仍有缺门牌时不能胡。
- 「是否强制优先打缺」由 `GameConfig.must_discard_missing` 控制（默认 `True`，符合多数川麻实现）。

### 2.3 行牌与响应

```
发牌 → 定缺 → 庄家出牌 → 循环：
  摸牌 → (自摸胡 / 暗杠 / 补杠)? → 出牌
       → 他家响应：胡 > 明杠 > 碰 > 过
       → 无人响应则下家摸牌
```

- **一炮多响**：同一张弃牌可被多家胡，点炮者分别赔付。
- 杠后补摸自摸胡 = **杠上花**；杠后打出的牌被胡 = **杠上炮**。

### 2.4 血战到底

- 一名玩家胡牌后**退出本局**（手牌冻结，不再摸打），其余人继续。
- 结束条件：只剩 **1 名**未胡玩家，或牌墙摸完（流局）。
- 一局可能产生 1–3 个赢家；最后未胡者承担流局结算。

### 2.5 计分

默认「番数 → `base_score × 2^番`」加倍制，可封顶。番型全部在 `FanConfig` 中配置（见附录 A）。

> **注意**：血战到底没有全国统一番表。上线前必须与目标平台逐项校准（见 §2.7）。

### 2.6 流局结算

- **查花猪**：流局时仍持有缺门牌者。
- **查大叫**：未听牌（无有效胡张）者。
- 当前引擎为**简化版**：花猪双倍赔付、未听牌向听牌者赔付，由 `GameConfig.draw_penalty` 控制，默认 0（关闭）。

### 2.7 规则差异矩阵（必须配置化）

| 规则项 | 常见取值 | 当前支持 |
|---|---|---|
| 换三张 | 开/关、方向、是否必须同花色 | 预留，未实现 |
| 门清是否计番 | 0 / 1 | `FanConfig` |
| 龙七对是否加根 | 加 / 不加 | `count_gen` |
| 自摸是否加番 | 0 / 1 | `FanConfig` |
| 刮风下雨支付 | 明/暗/补各异 | `GameConfig.gang_payment` |
| 抢杠胡 | 开/关 | **未实现**（番型已支持） |
| 一炮多响 | 开/关 | 已实现 |
| 流局查叫/查花猪 | 多种 | 简化版 |
| 封顶番数 | 3/4/5/无 | `cap_fan` |
| 连庄/多局积分 | 多种 | 未实现 |

## 3. 系统架构

### 3.1 分层

```
┌──────────────────────────────────────────────────────────────┐
│ 服务层   API / WebSocket / 房间管理 / 并发 / 灰度              │
├──────────────────────────────────────────────────────────────┤
│ 决策层   Policy Service                                      │
│          ├─ 规则策略 RuleAgent（BaselineAI，保底/降级）        │
│          ├─ 神经策略 NeuralAgent（BC / RL）                    │
│          └─ 后处理（安全牌、规则约束、超时降级）                │
├──────────────────────────────────────────────────────────────┤
│ 训练层   Self-play Runner / Replay Buffer / Trainer / League  │
├──────────────────────────────────────────────────────────────┤
│ 领域层   规则引擎 Game（状态机，唯一真值）                      │
│          ├─ 牌/手牌/向听/胡牌/听牌 Hand                        │
│          └─ 番型计分 Scoring                                  │
├──────────────────────────────────────────────────────────────┤
│ 基础层   牌编码 / 随机数 / 配置 / 日志                         │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 设计原则

1. **规则层与策略层彻底解耦**：策略只通过 `legal_actions()` / `view(seat)` 交互，便于替换算法与沙箱评估。
2. **引擎是唯一真值**：合法性、结算、血战流程全部由引擎保证，AI 无法绕过。
3. **配置化规则**：定缺强制、番值、封顶、杠结算、流局赔偿全部可配。
4. **可复现**：`Game(seed=...)` 完全确定，便于回归与自博弈复现。
5. **训练/线上同源**：训练、评估、线上对战复用同一份引擎，避免规则漂移。

## 4. 规则引擎设计

### 4.1 牌编码

- `0..26`：`0..8=万`、`9..17=筒`、`18..26=条`。
- 手牌用 `count[27]` 计数向量：天然适配神经网络特征，且节省内存。
- 不变量：`sum(count) = 13 - 3×副露数`（摸牌后 +1）；每种牌 ≤ 4。

### 4.2 向听数

`shanten(counts, exposed_melds)` 取标准型与七对型的较小值：

- **标准型**：`8 - 2×面子 - min(搭子, 4-面子) - 有将`，DFS 枚举刻子/顺子/对子/搭子/弃牌。
- **七对型**（仅门清）：`6 - Σ floor(count_i/2)`；四张算两对（龙七对）。

当前实现用 `lru_cache` 记忆化 DFS。实测（本机）：

| 场景 | 吞吐 |
|---|---|
| 13 张随机手牌 | ≈ 4,988 手/秒 |
| 14 张随机手牌 | ≈ 4,012 手/秒 |

**生产优化路线**：
1. 按花色预计算「9 张牌型」最优拆解表（`5^9 ≈ 1.95M` 状态，可离线生成），三花色查表合并；
2. 或用 Rust/C++ 重写热路径（PyO3 暴露）；
3. 目标：单次向听 < 10 µs。

### 4.3 胡牌与听牌

- `is_winning(counts, exposed_melds, missing_suit)`：先校验缺门，再判标准型或七对/龙七对。
- `winning_tiles(...)`：枚举 27 种牌，返回胡张（排除缺门与已见满 4 张）。
- `ukeire(...)`：进张 = 摸入后「最优弃牌」能使向听下降的牌，返回剩余张数。
- `best_discards(...)`：最小化向听的弃牌集合，供规则 AI 使用。

### 4.4 计分

`score_win(WinContext, FanConfig) -> ScoreResult(fan, items, points)`：

- 输入：暗牌计数、副露、胡牌张、自摸/点炮、情景标记（杠上花/杠上炮/抢杠/海底/天胡/地胡）、缺门。
- 输出：`items` 为可解释番型明细（如 `["清一色", "根x1"]`），便于复盘与对账。
- 牌型番互斥，叠加番累加，最后按 `cap_fan` 封顶。

### 4.5 对局状态机

`Game` 是**反应式状态机**，调用方按 `legal_actions()` → `step(action)` 推进：

| 阶段 | 含义 | 当前行动者 |
|---|---|---|
| `MISSING` | 定缺 | 按庄家起的顺序逐人选择 |
| `TURN` | 摸牌后行动 | `game.turn` |
| `REACTION` | 他家响应弃牌 | `reaction.order[idx]` |
| `OVER` | 结束 | — |

关键机制：
- **动作白名单**：`legal_actions()` 是唯一合法动作来源，`step()` 会校验，杜绝非法动作。
- **血战**：赢家 `won=True` 后从轮转中剔除。
- **一炮多响**：响应阶段收集全部 `HU_DISCARD` 后统一结算。
- **零和**：所有分值为玩家间转移，测试断言 `sum(scores) == 0`。

### 4.6 性能预算

| 操作 | 当前 | 目标 |
|---|---|---|
| 向听 | ~0.2–0.25 ms | < 10 µs（查表） |
| 单局模拟 | 需补基准 | ≥ 1 万局/核/小时（Rust） |
| 单步推理 | — | < 50 ms（含网络） |

## 5. 状态与动作空间

### 5.1 状态（AI 可见信息）

| 信息 | 维度 | 可见性 |
|---|---|---|
| 自己手牌 | 27 计数 | 私有 |
| 自己副露 | 碰/杠列表 | 公开 |
| 四家牌河 | 4 × 27 | 公开 |
| 四家定缺 | 4 | 公开 |
| 四家是否已胡 | 4 | 公开 |
| 剩余牌墙 | 1 | 公开 |
| 分数 | 4 | 公开 |
| 对手手牌 | — | **不可见**（只能推断） |

引擎通过 `game.view(seat)` 只暴露上述信息，从接口层面杜绝作弊。

### 5.2 动作空间

| 阶段 | 动作 | 规模 |
|---|---|---|
| 定缺 | 选 0/1/2 门 | 3 |
| 出牌 | 打出一张 | ≤ 27（去重后通常 ≤ 14） |
| 自身回合 | 自摸胡 / 暗杠 / 补杠 | ≤ 5 |
| 响应 | 胡 / 明杠 / 碰 / 过 | ≤ 4 |
| 换三张 | 选 3 张同花 | ≤ ~500（未实现） |

**关键点**：动作空间远小于围棋；难点在**不完全信息**与**多人计分博弈**。

### 5.3 神经网络特征（建议）

总维度约 500–900：

| 特征 | 维度 | 说明 |
|---|---|---|
| 自家手牌计数 | 27 | 除以 4 归一化 |
| 自家副露 | 4×(27+2) | 槽位 + 牌 one-hot + 类型 |
| 各家牌河 | 4×27 | 计数 |
| 各家定缺 | 4×3 | one-hot |
| 已见牌计数 | 27 | 全局可见张数 |
| 牌墙剩余 | 1 | 归一化 |
| 分数 | 4 | 归一化 |
| 当前行动者 | 4 | one-hot |
| 是否已胡 | 4 | 0/1 |
| 合法动作掩码 | ~40 | 与动作头对齐 |

### 5.4 统一动作头

建议 **统一 40 维动作头 + 掩码**：非法动作置 `-inf` 后 softmax，避免多头耦合与非法采样。

## 6. AI 技术路线

### 6.1 阶段总览

```
阶段 A 规则基线（已完成）
   └─ 向听驱动 + 危险牌启发式
阶段 B 监督学习（BC）
   └─ 人类/基线牌谱 → 策略网络
阶段 C 强化学习自博弈
   └─ PPO + 对手池 + 全局奖励预测
阶段 D 混合与产品化
   └─ 规则兜底 + 模型主决策 + 复盘解释
```

### 6.2 阶段 A：规则基线（已实现）

- 定缺：选「最弱」花色（张数/对子/连张加权）。
- 出牌：最小化向听；平局按「孤张优先、已见牌优先（更安全）」。
- 碰：碰后向听不劣化才碰；杠默认接受。

**实测强度**（60 局，2 基线座 vs 2 随机座，轮转座位）：

| 座位 | 平均得分/座 | 胡牌次数 |
|---|---|---|
| 基线 | **+1.750** | 76 |
| 随机 | -1.750 | 1 |

差值为 **+3.5 分/座**，说明基线已明显强于随机，可作为评估下限与训练陪练。
（样本量小，仅作方向性结论；正式评估需 ≥ 1000 局。）

### 6.3 阶段 B：监督学习（BC）

- **数据**：真人高段位牌谱优先；不足时用基线 AI + 规则扰动 + 搜索生成。
- **目标**：给定观测预测专家动作（出牌为主，碰/杠/胡为辅）。
- **损失**：掩码交叉熵 + 价值回归 + 辅助头（胡牌概率、向听）。
- **产出**：一个「像人」的初始策略，为 RL 提供良好起点。

### 6.4 阶段 C：强化学习自博弈

参考微软 Suphx 的范式（**不是** AlphaZero 的直接套用——麻将是不完全信息、四人不确定博弈）：

1. **自博弈**：4 个当前策略副本对局，记录 `(obs, action, logp, reward, mask)`。
2. **奖励**：以「局终得分变化」为主信号（天然零和）；可加名次奖励、番数塑形。
3. **全局奖励预测**（Suphx 的 global reward prediction）：辅助头预测最终得分，缓解稀疏奖励。
4. **算法**：PPO（稳定、易调）；可对比 A2C / NFSP。
5. **对手池（League）**：历史 checkpoint + 基线 + 随机混合采样，防止「只赢自己」退化。
6. **课程学习**：先固定定缺/简化番型，再放开完整规则。

### 6.5 阶段 D：混合与产品化

- **规则兜底**：模型超时/异常时回退 `BaselineAI`。
- **难度分级**：不同 checkpoint 对应不同难度。
- **复盘解释**：番型明细 + 关键决策对比生成文字复盘（LLM 的合理位置）。
- **持续学习**：线上对局脱敏回流，定期增量训练。

### 6.6 为什么不用 LLM 直接出牌

| 维度 | LLM | 专用策略网络 |
|---|---|---|
| 精确计数（27 种牌、剩余张数） | 易错 | 原生 |
| 单步延迟 | 数百 ms～秒级 | < 50 ms |
| 训练成本 | 极高 | 低 |
| 对局强度 | 弱 | 强（可超人类） |
| 可解释性 | 语言解释强 | 需额外模块 |

**结论**：LLM 用于复盘解说、规则问答、数据标注，不进入实时决策环。若必须使用，做「LLM 高层意图 + 规则/策略网络执行」的混合，而非端到端。

## 7. 模型选型

### 7.1 网络结构

```
输入特征 (~700 维)
   │
   ├─ MLP: 700 → 512 → 512 → 512（ReLU + LayerNorm）
   │        或 ResNet block × 4
   │
   ├─ policy head : 40（统一动作空间，掩码 softmax）
   ├─ value head  : 1（预期局终得分）
   └─ aux heads   : 胡牌概率、向听、对手听牌概率（可选）
```

- 参数量 **1–5M**，单卡可训，CPU 推理可行。
- 麻将属于「小状态、强组合」问题，**特征工程 + 中等网络** 优于堆大模型。

### 7.2 训练算法

| 阶段 | 算法 | 数据 | 目标 |
|---|---|---|---|
| B | 行为克隆（交叉熵） | 人类/基线牌谱 | 模仿 |
| C | PPO（clip） | 自博弈 rollout | 最大化期望得分 |
| C+ | PPO + League + 全局奖励预测 | 自博弈 + 对手池 | 稳定提升 |

PPO 起点超参（需调）：`lr=3e-4`、`clip=0.2`、`γ=0.99`、`GAE λ=0.95`、`batch=4096 steps`、`epochs=4`。

### 7.3 算力估算

- 单局自博弈以 CPU 为主（引擎），GPU 只做批量推理。
- 起步：**8–16 核 CPU + 1×RTX 4090/A10**；规模扩大后加 worker。
- 训练时长：BC 数小时；RL 到可用强度约 1–3 周（取决于引擎吞吐，需基准后细化）。
- 推理：ONNX / TorchScript，CPU 单核 < 10 ms（网络部分）。

## 8. 训练系统

### 8.1 数据流

```
Self-play workers (CPU, N 进程)
   → 轨迹 (obs, action, logp, reward, mask)
   → Replay Buffer（共享内存/队列）
   → Trainer (GPU, PPO)
   → 新 checkpoint
   → 评估（vs 基线/历史）→ 通过则入 League
```

### 8.2 并行架构

- **进程级并行**：每个 worker 独立跑 `Game`，绕开 GIL。
- **批量推理**：worker 把观测发到推理服务，攒批后 GPU 前向，回传动作。
- **引擎加速**：若 Python 吞吐不足，优先把 `shanten` / `Game` 热路径下沉 Rust（PyO3）。

### 8.3 工程要点

- 固定随机种子，保证可复现。
- 每次训练记录：规则配置哈希、引擎版本、数据版本、超参。
- 模型与规则版本绑定，避免「新模型 + 旧规则」错配。

## 10. 评估体系

### 10.1 离线指标

- 动作准确率（对牌谱）。
- 向听效率（平均向听下降速度）。
- 放炮率、听牌率、平均番数。
- 规则覆盖率。

### 10.2 在线对战评估

固定种子、固定对手池，跑 N 万局：

- 平均得分、胜率、名次分布。
- 对 `BaselineAI`、随机策略、历史版本 的胜率矩阵。
- 血战特有：平均「血战轮数」、被一炮多响率。

### 10.3 Elo

以 `BaselineAI` 为锚点（Elo 1500），成对对战更新。上线门槛：相对上一版本胜率 ≥ 52% 且置信区间下界 > 50%。

### 10.4 当前实测基线

| 测试 | 结果 |
|---|---|
| 测试套件 | 392 项全绿（342 整局 + 32 手牌 + 18 计分） |
| 向听吞吐 | 13 张 ≈ 4,988/s；14 张 ≈ 4,012/s |
| 基线 vs 随机（60 局） | 基线 +1.75/座，随机 -1.75/座 |

## 11. 服务与部署

### 11.1 推理服务

```
Client ──WS/HTTP──> Gateway ──> Policy Service（模型）
                                   └─ fallback: RuleAgent
```

- 无状态推理，水平扩展。
- 模型热加载 + 灰度（按房间/用户分桶）。
- 超时（如 100 ms）自动回退规则 AI。

### 11.2 协议

- 请求：`{hand, melds, discards, missing, wall_left, legal_actions}`
- 响应：`{action: {kind, tile}, confidence, fallback: bool}`
- 建议 protobuf（低延迟）或 JSON（易调试）。

### 11.3 延迟预算

| 环节 | 预算 |
|---|---|
| 网络 | < 10 ms |
| 特征编码 | < 2 ms |
| 模型前向（CPU） | < 20 ms |
| 后处理/校验 | < 2 ms |
| 合计 P99 | < 50 ms |

## 12. 当前实现状态

### 12.1 已验证

- **392 项测试全绿**：含 120 局随机对局、40 局规则 AI 对局，零和校验通过。
- 覆盖：向听/胡牌/七对/龙七对/缺一门/番型/碰杠胡/一炮多响/杠后补牌。
- 性能：向听 ≈ 4,000–5,000 手/秒（纯 Python）。
- 强度：基线对随机 +3.5 分/座（60 局）。

### 12.2 已知差距（按优先级）

1. **抢杠胡**未接入引擎（番型已支持）。
2. **换三张**未实现。
3. **流局结算**（查花猪/查大叫）为简化版，需按平台校准。
4. **向听性能**：纯 Python 约 4k 手/秒，自博弈训练需优化。
5. **无学习型策略**：目前只有规则 AI。
6. **无多局积分/连庄**。

### 12.3 性能优化路线

1. 向听改为按花色预计算 DP 表（预计 10–50×）。
2. 热点迁 Rust/C++（PyO3），规则层保持 Python 接口。
3. 自博弈并行：多进程 + 共享模型（或向量化环境）。

## 13. 风险与合规

1. **规则差异（最高风险）**：血战没有唯一标准。上线前必须与目标平台逐项对齐番表、刮风下雨、抢杠、流局、封顶、一炮多响、连庄。建议建立「规则对账集」：用平台真实牌谱回放，逐局比对结算。
2. **法律风险**：若涉及真实货币/兑换，可能触及博彩监管。必须确保无真实货币交易、无兑换通道，并咨询专业法律意见。
3. **开源许可证**：参考开源项目需核实许可证；GPL/AGPL 不可直接闭源商用；无许可证默认不可用。策略：规则引擎自研，仅参考架构与算法思想。
4. **数据合规**：人类牌谱需授权；用户数据需脱敏。
5. **公平性**：AI 不得读取隐藏信息（引擎已通过 `view(seat)` 隔离）。
